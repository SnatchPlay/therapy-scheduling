# 0005. Колонковий update статусу страхування: лише планувальник і адміністратор, правило в базі

- Статус: прийнято (доповнює 0004, не замінює)
- Дата: 2026-11-08
- AC: AC-INS-01, 02, 03, 04, 05 (зріз 3, WS9); AC-INS-06 (без входу) діє за 0004 без змін

## Контекст

ADR 0004 («Колонки») каже: «update і delete для authenticated немає (редагування — після WS11)». Зріз 3 вимагає, щоб
планувальник і адміністратор позначали в картці клієнта статус перевірки страхування («Verified», «Not accepted»,
«Private pay») і змінювали його між ними, а терапевт лише бачив статус у картках своїх клієнтів
(`requirements/33-planuvalnyk-poznachaie-status-perevirky.md`, матриця прав у `requirements/product.md`). Публічний ключ
Supabase лежить у браузері, тож Data API може викликати будь-хто: правило «лише планувальник чи адміністратор» мусить
виконувати база, а не сторінка чи server action.

## Рішення

- **Колонка.** `public.clients.insurance_status text not null default 'Not set'` з `check` на чотири значення. `default`
  дає «Not set» усім наявним карткам зрізів 1–2 без окремого оновлення даних (AC-INS-01).
- **Право лише на цю колонку.** `grant update (insurance_status) on public.clients to authenticated`; `anon` не має нічого,
  `delete` лишається без права, решта колонок картки — без `update` (редагування картки — після WS11, як у 0004).
- **Політика `clients_update_insurance_staff`** (`for update to authenticated`): `using (private.is_scheduler_or_admin())`
  і `with check (insurance_status in ('Verified', 'Not accepted', 'Private pay'))`. Терапевт політики на `update` не має:
  його запит зачіпає нуль рядків, статус не змінюється (AC-INS-05). `with check` дає правило PM «„Not set“ — лише
  початковий, повернути не можна» без тригера.
- **Читання без змін:** статус бачить той, кому RLS віддає картку (`clients_select_staff`, `clients_select_therapist` через
  `private.own_client_ids()`), тож терапевт бачить його лише в картках своїх клієнтів (AC-INS-04).
- **Код лише перекладає.** Server action `setInsuranceStatus` викликає `getViewer()` першим оператором (0004), не
  перевіряє роль сама й вважає збереженням тільки один зачеплений рядок.
- **Супутня зміна.** `clients_complete_check` (`not valid`) перевірявся б і на update старої картки зрізу 1, тож повноту
  нової картки тепер виконує тригер `after insert` з тією самою помилкою (дизайн-план `impl-insurance-status`, Р27).
- **Межа рішення.** Наступна колонка картки, яку можна змінювати, — окреме рішення (новий ADR): цей дозволяє `update` лише
  для `insurance_status`.

## Розглянуті варіанти

- Функція `rpc` `set_insurance_status` (security definer) — ні: одна колонка й одне правило, їх повністю виражають право
  на колонку й політика; `rpc` потрібні для кількох записів або перевірки разом із записом (`AGENTS.md`, розділ «База даних»).
- Перевірка ролі в server action (`if role !== …`) — ні: Data API оминає дію; це суперечило б 0004.
- Тригер, що забороняє повертати «Not set» — ні: те саме дає `with check` політики, без ще однієї функції.
- Окрема таблиця статусів — ні: один поточний статус на клієнта; історія змін поза межами вимоги PM.

## Наслідки

Таблиця `clients` уперше має політику й право на `update`, тож кожна нова колонка з правом `update` потребує власного
рішення й тесту «дозволено / відмовлено / дані не змінились» (скіл `rls-migration`). Тести бази
(`tests/db/insurance-status-db.test.ts`) червоніють без права, без `using` чи без `with check`. Якщо PM попросить історію
змін статусу або редагування картки, це нове рішення: таблиця історії чи розширення прав, а не правка цього.
