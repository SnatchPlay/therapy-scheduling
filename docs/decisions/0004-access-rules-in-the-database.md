# 0004. Доступ: правила в базі, «свій клієнт» — явна множина, користувач без ролі, перевірка сесії в кожній дії

- Статус: прийнято
- Дата: 2026-10-26
- AC: AC-CARD-04, 05, 06, 07, 08, 09, 10, 11 (зріз 2, WS7 завдання C і D); AC-HOLD-08, 14 (ролі зрізу 1 діють без змін)

## Контекст

Публічний ключ Supabase лежить у браузері, тож Data API (PostgREST) може викликати будь-хто, минаючи сторінки й server
actions. Зріз 2 уперше дає терапевту персональні дані клієнтів (дата народження, мова, дані опікуна) і вимагає, щоб він
бачив лише власних: «Held» або «Confirmed» у його слотах (`requirements/product.md`, «Свій клієнт»). Користувач без ролі
не має бачити нічого (AC-CARD-11). Кожен експорт файлу з `"use server"` — публічний POST-ендпойнт, який можна викликати
напряму: без перевірки сесії дія була б відкритою.

## Рішення

- **Роль у таблиці, не в токені.** Роль — `public.profiles.role` (`admin`, `scheduler`, `therapist` або `null`), її
  читає `private.current_app_role()` (security definer). JWT і `user_metadata` керує користувач або дозволяє підробити
  при реєстрації; саму роль (`role`) змінює лише `service_role` (користувач може змінити лише власне `full_name`). Роль
  без значення (`null`) — «без ролі»: хелпери не дають доступу (`is_scheduler_or_admin` повертає `false`,
  `current_therapist_id` — порожньо), жодна політика такого користувача не пускає. Раніше нова людина без ролі ставала `therapist`; найменші права
  означають «жодних».
- **«Свій клієнт» — явна множина в базі.** `private.own_client_ids()` (security definer, `set search_path = ''`) повертає
  клієнтів з утриманням «Held» (не прострочене) або «Confirmed» у слотах поточного терапевта; політика
  `clients_select_therapist` читає `id in (select private.own_client_ids())`. Раніше політика спиралася на RLS таблиці
  `holds` («власні, не прострочені») і зміна `holds_select` мовчки відкрила б чужих клієнтів; тепер правило про
  клієнтів живе в одному місці, а тест AC-CARD-04/05/08/09 червоніє без нього.
- **Колонки.** `grant insert` лише на колонки картки; `created_by`, `created_at`, `id` ставить база; `update` і
  `delete` для `authenticated` немає (редагування — після WS11). Створює картки лише `private.is_scheduler_or_admin()`
  (політика `clients_insert_staff`); для терапевта insert відмовляє RLS, а дія (`getViewer`, без перенаправлення за роллю)
  лише перекладає цю відмову на текст PM (AC-CARD-06).
- **Сторінки не дублюють правил.** `/clients` і `/clients/[id]` роблять один запит для всіх ролей, а що побачить
  користувач, вирішує RLS: чужа й неіснуюча картка — нуль рядків, терапевт бачить ту саму відмову без даних (не
  розкриваємо, хто є клієнтом практики), планувальник — 404.
- **Сесія в кожній дії.** Першим оператором кожної server action має бути виклик `getViewer()` або `requireRole()`
  (`@/lib/supabase/viewer`): вони викликають `supabase.auth.getClaims()` (перевіряє підпис JWT; `getSession()` не
  використовуємо) і повертають клієнт Supabase цього користувача, тож до сесії немає ні запитів, ні побічних ефектів.
  Виняток — `login` і `signOut`. `requireRole` у сторінках — лише маршрутизація (куди повернути користувача); у діях,
  де потрібен текст відмови від бази, беремо `getViewer`, а доступ вирішує база.
- **Правило, яке це перевіряє.** `scripts/check-action-auth.mjs` (`npm run check:actions`, job «Server actions: сесія
  перевіряється» в `architecture.yml`) розбирає код компілятором TypeScript, а не регулярними виразами. Порушення:
  перший оператор тіла не є викликом `getViewer`/`requireRole`, імпортованих з `@/lib/supabase/viewer` (виклик під
  `if`, після іншого коду, власна функція з такою назвою, імпорт з іншого модуля); експорт файлу з `"use server"`, що не є
  `export async function` (стрілка, клас, `enum`, `export { … }`, `export *`, `export default <вираз>`, генератор, синхронна
  функція); inline-директива `"use server"` у функції будь-якого файлу без такої самої перевірки.

## Розглянуті варіанти

- Роль у JWT (`app_metadata`) і перевірка в політиках через `auth.jwt()` — ні: роль змінюється рідко, але відкликати її
  до закінчення токена не можна, а профіль уже є джерелом істини для всіх хелперів.
- Лишити політику клієнтів на підзапиті до `holds` — ні: працює, але правило про клієнтів залежить від чужої політики
  (див. вище); явна функція коштує п'ять рядків і дає власний тест.
- Перевіряти доступ у server actions і сторінках (`if role !== …`) — ні: Data API їх оминає; код лише перекладає
  відмови бази в повідомлення. Єдина перевірка в коді — що сесія є (`getClaims`), бо без неї немає клієнта Supabase з
  правами користувача.
- Правило через ESLint — розглянуто; скрипт без залежностей простіший, виконується окремим job і має власні тести.

## Наслідки

Нова таблиця з персональними даними починається з політик і прав у міграції та тесту «allowed, refused, data
unchanged» (скіл `rls-migration`); нова server action без `getViewer()`/`requireRole()` не пройде `architecture`.
Job `architecture` не входить до обов'язкових перевірок ruleset `solo-main` (як у ADR 0002): червоний прогін видно в
PR, але merge він не блокує, поки власник не додасть його в ruleset.
Межі правила: скрипт бачить, що сесію викликано першим оператором, а не що роль підходить: роль перевіряють RLS і функції
бази, їхні тести — `tests/db/*.test.ts`. Файли `route.ts` (GET/POST) він не перевіряє: у репо їх немає, а з'явиться —
правило розширюють. Job потребує `npm ci` (компілятор TypeScript — devDependency), тож повільніший за інші правила
architecture; це запобіжник від забутої перевірки, а не доказ безпеки.

## Як перевіряємо

`tests/db/client-card-db.test.ts` — по тесту на кожну відмову AC-CARD (без політики, права чи обмеження тест червоніє:
таблиця мутацій у PR задачі 8). `tests/scripts/check-action-auth.test.ts` — 15 тестів: правило
ловить дію без перевірки сесії, перевірку не першим оператором (під `if`, після іншого коду, після виклику хелпера),
підроблену чи не з того модуля `getViewer`, inline-дію й експорти, яких не можна перевірити; кожне правило скрипта
мутовано вручну (мутант без нього червонить тест); на реальному репо правило проходить. Червоний прогін CI на
`mutation:`-коміті з дією без `getViewer()` і його відкат — у PR задачі 11.
